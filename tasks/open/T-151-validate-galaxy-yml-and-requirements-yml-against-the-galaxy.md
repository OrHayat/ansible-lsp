# T-151 — Validate galaxy.yml and requirements.yml against the galaxy schemas

| Status | Kind | Priority | Size | Depends on |
| ------ | ---- | -------- | ---- | ---------- |
| open   | task | P3       | M    | —          |

## Problem

Both files have real, core-owned schemas and zero coverage from us:

- **`galaxy.yml`** (collection manifest) is the easy half: core ships a machine-readable
  schema — `galaxy/data/collections_galaxy_meta.yml`, one entry per key with
  `required`/`type` — the same way `config/base.yml` describes settings. A missing
  `namespace`/`name`/`version`/`readme`/`authors` fails `ansible-galaxy collection build`
  outright.
- **`requirements.yml`** is looser: `cli/galaxy.py:778-834` accepts a list (legacy role
  format) or a dict whose only meaningful keys are `roles:` and `collections:`, and errors
  on anything else ("Expecting requirements yaml to be a list or dictionary").
  Per-entry keys (`name src version type scm include signatures`) are validated further
  down the same file.

We already point users at `requirements.yml` (the demo carries one) without reading it.

## Approach

`galaxy.yml` first — transcribe `collections_galaxy_meta.yml` the way `keywords.rs`
transcribes FieldAttributes (checked-in snapshot, regenerated by diff), flag unknown keys
and missing required ones. File-kind is by name + position (collection root). Then the
`requirements.yml` shape checks, transcribed from a whole read of the consuming code in
`cli/galaxy.py`, not from docs. Severity per what the CLI actually does: build/install
failures are ERRORs, tolerated oddities stay silent.

## Done when

- [ ] unknown / missing-required keys in `galaxy.yml` are flagged, set transcribed with
      the source snapshot version recorded
- [ ] `requirements.yml` top-level and per-entry shape checked per `cli/galaxy.py`, with
      cites; the legacy list format stays legal
- [ ] `# noqa`-suppressible, zero false positives on the demo files
